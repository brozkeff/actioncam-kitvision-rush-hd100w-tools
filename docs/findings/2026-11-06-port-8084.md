# Port 8084 camera HTTP service

## Identity and observed behavior

The active `/etc/rc.d/rcS` starts `/bin/http` in the background. Static
disassembly of that exact MIPS binary shows it creates an IPv4 TCP listener and
binds port `8084`. The process and port were also observed on the camera. This
identifies `/bin/http` as the service managing 8084 on the inspected firmware.

The Android APK contains `http://192.168.1.2:8084/?stream`. A request to that
URL returned HTTP 200 with `application/octet-stream`, but no 4096-byte body
arrived before the request timed out. This establishes that the listener
responded, but not that a usable video stream was delivered.

The decoded Android app's `ActionTabActivity$28.run` calls
`WiFiJNI.startRealtimeStream()`, returns early on a nonzero result, waits
two seconds, and then passes the URL to `nativeInit`. The Java wrapper calls
the native `ProtocolSwitchRealtime` function. In `libaction.so`, that JNI
function passes `Real_Time` to a shared mode-switch routine. The routine copies
12 bytes into the request and sends family 255, command 3 with a timeout field
of 10000. This matches the existing Python mode command; successful switching
and the two-second wait are app-side prerequisites before opening the stream.
The remaining camera-state prerequisites require further tracing, and the
sequence alone does not explain the stalled response.

No source code for `/bin/http` is present in the dump. Offline disassembly and
the related, older `/cgi-bin/http` binary show HTTP request parsing, file
response handlers and byte-range response code. The sibling binary explicitly
parses `GET <path> HTTP/<version>`, opens `/dev/CAM00`, and contains 200, 206,
400, 404 and 500 response paths. Both binaries include file MIME names such as
HTML, JPEG, MOV, MP4 and a generic octet-stream fallback. The active binary
contains the same request parser and file-handler identifiers, but its stripped
build differs from the sibling; do not assume every detail of that older
handler is identical without a request trace.

There is no clear table of named REST-style routes in the active binary. The
best-supported model is a generic HTTP request-target/file handler, with
`/?stream` as the vendor app's special-looking request. The actual meaning of
the `stream` query, exact path namespace, and whether ordinary camera files
are served by the active build remain unverified. Directory listing was not
found in the sibling handler; directory paths appear to follow its 404 path.

## What it can do and side effects

Static binary evidence includes `/dev/CAM00`, the strings `read_cam_file_only`,
`restore_usb`, `close_usb`, `remote setmode realtime2` and `/tmp/realtime`, as
well as imports for device I/O, process execution, sockets and file reads.
Together these indicate that the service interacts with the internal camera
processor and its USB/realtime mode, rather than acting as another copy of the
8083 static root filesystem. A request may trigger or depend on a transition
into realtime mode and a later restore/close path. The exact request-to-mode
sequence has not been traced end to end, so treat calls as potentially
state-changing.

The exposed behavior supported by static evidence is:

- HTTP request parsing and error responses.
- File-like response handling, including HTTP byte ranges in the sibling
  implementation. This could support resumable retrieval of large clips if
  the active service exposes them at known paths.
- A vendor-requested stream path (`/?stream`) intended for realtime viewing.
- Internal camera/USB interactions and realtime-mode handling.

No active-binary route was identified for formatting the card, changing
settings, uploading firmware, rebooting, or starting/stopping recordings. Those
operations are present in other interfaces or binaries, but should not be
attributed to port 8084 based on the evidence here. The port 80 CGI actions and
port 6667 binary commands are separate service surfaces.

## Useful follow-up

If doing a live check on the owner's camera, keep it bounded and start with the
vendor `/?stream` URL in the camera's expected `Real_Time` state. Capture full
response headers and a short body with a strict timeout. If the service proves
to be a file handler, use only a known owner-created media filename and test a
small byte range before attempting a full download. Record camera mode before
and after each request because the binary references realtime/USB transitions.
Avoid guessing action paths or sending write methods: static analysis has not
established a safe write API.

Evidence artifacts are private under ignored `tmp/camera/http-analysis.*`,
`tmp/camera/cgi-http.*` and the previously captured
`tmp/camera/http-read-exposure.json`; no vendor binary or raw output is tracked.
